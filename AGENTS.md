# Working on this repository (for AI assistants and the people using them)

Read this whole file before changing anything. People have a shorter version in
[docs/contributing.md](docs/contributing.md). Both must say the same thing: if you change a rule,
change it in both. Details live in [README.md](README.md) and [docs/](docs/).

## What this is
The website for Franciscan University's Department of Engineering and Computing: projects,
faculty, students, a degree planner, student accounts with a review queue, and admin editing.
React 19, React Router 7, TypeScript, Vite, Tailwind 4, anime.js; Supabase (Postgres, sign-in,
photo storage, edge functions); Cloudflare Pages. It is a student project with several people
working at once, so small, reviewable changes matter more than clever ones.

## Branches and releases (the most common mistake)
Every change takes one path: **feature branch -> `staging` -> `main`**.

- `staging` is the developer site (https://staging.csc-dept-website.pages.dev) on the **dev** database.
  `main` is the **live** site on the **production** database.
- Start every branch from an up-to-date `staging` and open the pull request **into `staging`**, never `main`.
  Only a pull request from `staging` into `main` publishes the site.
- Name branches `feature/short-description`, `fix/...` or `docs/...`. Push to this repository, not a fork, so the pull request gets a preview link.
- Never push to `staging` or `main` directly, never force-push them, and never push a branch's migrations to the dev project by hand: merging to `staging` applies them. A hand-pushed migration blocks every later dev deploy until that branch merges.
- Comment on the issue before starting ("Working on this one.") so nobody else picks it up.
- A pull request needs one approving review from a code owner, and both checks ("Lint, unit tests and build" and "Database, API and browser tests") must pass. Pushing new commits dismisses an approval, so finish before asking for review. You cannot approve your own pull request.

## The change-log: required on every pull request
There is no shared CHANGELOG file. Each pull request description carries its own entry under a
**What changed** heading, written in plain words for someone who uses or runs the site and has
not read the code: a few bullets of what is different now ("Students can now ...", not which
files you edited). A check fails the pull request until it is filled in.

- Mention database changes, new settings or secrets, and anything a teammate must do after merging.
- If you are an AI assistant opening or updating a pull request, write this section yourself from the actual diff. Never leave the template's placeholder, and never describe work you did not do.
- `npm run changes` lists everything merged into `staging` since the latest version tag (`v0` is the site as first shown, 2026-10-20); see [docs/change-log.md](docs/change-log.md).
- Pull request descriptions follow [.github/pull_request_template.md](.github/pull_request_template.md): `Closes #<issue>`, What changed, How to check it on the preview, the checklist.

## Issues
Every issue has a **Size** (tier 1 to 4) and a priority (P1 to P3); see
[docs/issue-sizes.md](docs/issue-sizes.md). Tier 4 work starts with a short plan posted on the issue.
Anything touching sign-in, permissions or student-only content also gets the `security` label.
Use the issue forms in `.github/ISSUE_TEMPLATE/`. Do not create issues, labels or comments on
GitHub unless the person you work for asked for it.

## Where things live
| Path | What it is |
| --- | --- |
| `src/pages/` | One component per page. `account/` is sign-in and the student forms, `review/` the reviewer queue |
| `src/components/` | Shared pieces: header, footer, forms, carousel, project browser, editable text |
| `src/lib/` | Everything that is not drawing. `content.ts`, `account.ts`, `review.ts`, `people.ts`, `siteText.ts` and `planner/` are the **only** files that talk to Supabase |
| `src/lib/database.types.ts` | Generated by `npm run db:types`. Never edit by hand |
| `src/index.css` | Color tokens (light and dark) and motion timing |
| `public/_headers` | Security headers and the Content-Security-Policy. A new outside address (image host, API) must be added here or the browser blocks it |
| `supabase/migrations/` | The schema and access rules, in order. `supabase/tests/` holds the database and API tests |
| `tests/e2e/` | The browser test of the student forms and review queue |
| `docs/` | `frontend-explained.md` and `backend-explained.md` explain how it all works; read the relevant one before a non-trivial change |

## Rules for the code
- **Mobile first.** It must work at 375, 768 and 1280 px with no horizontal scroll, and every button and link target is at least 44 px tall (`min-h-11`).
- **Colors come from the theme tokens** in `src/index.css`, never hard-coded, and must look right in light and dark.
- **One `h1` per page**, headings in order, a visible label on every form control, alt text on every meaningful image (decorative ones hidden from screen readers), and a page title via `useTitle`.
- **Motion is subtle and respects reduced motion.** Load anime.js only through `src/lib/motion.ts`. Nothing may stay hidden if animation fails.
- **Content lives in data**, not in pages: the database (`site_content` for editable wording, tables for people and projects) or the files in `src/lib`. Do not hard-code lists of courses, people or events into components.
- **Load data with `useAsync` / `useReloadable` / `useAction`** from `src/lib/hooks.ts`, and show "Loading..." and failure states. Put new reads and writes in the matching `src/lib` file, not in a component.
- **The browser is never trusted.** A role check on screen must be repeated by the database (row level security). Visitors may only see published projects and students who opted in. Anything student-only or admin-only needs a database rule and a test, not just a hidden button.
- **Text people type is data.** Render it through React (escaped) or `src/lib/markdown.ts`; never use `dangerouslySetInnerHTML` or build HTML from user input. Links to outside sites use `rel="noopener noreferrer"`.
- **Keep libraries small.** Load large ones lazily (`import()`), as `markdown-to-jsx` and `exceljs` already are. Ask before adding a dependency; there is no UI kit or state library on purpose.
- Match the surrounding code: naming, comment density, and idiom. Do not reformat files you are not changing. Keep line endings as the file already has them (`README.md` and the pull request template use CRLF).

## Database changes
- Schema changes are migration files only: `npx supabase migration new short_name`, then write SQL under `supabase/migrations/`. Never change tables in the hosted dashboard.
- Never edit a migration that has been merged; write a new one.
- New tables need row level security, only the grants they need, and pgTAP tests in `supabase/tests/database/`. Run `npm run db:types` and commit the result.
- Test locally with `npm run db:start` (needs Docker) and `npm run db:reset` after pulling new migrations. Hosted databases change only through the merge flow above.

## Checks to run before opening a pull request
| When | Run |
| --- | --- |
| Always | `npm run lint`, `npm run test:unit`, `npm run build` |
| Touches the database or carousel | `npm run db:test`, `npm run test:api`, `npm run test:carousel` |
| Touches sign-in, student forms or the review queue | `npm run test:e2e` |

Add or update tests for what you changed. If a check fails, fix it or say so plainly in the pull
request; never claim something was tested if it was not.

## Never
- Commit secrets: `sb_secret_...`, database passwords, `supabase/functions/.env`, `.env.local`. The site uses the publishable key only.
- Skip hooks or checks, disable a lint rule to get past it without a reason in a comment, or weaken a security header or access rule to make something work.
- Do something outward-facing (push, open or merge a pull request, comment, change GitHub settings, touch a hosted database) without the person you work for asking for it.

## Commits and pull requests made by an AI
End commit messages with the attribution line your tool gives you (for Claude Code,
`Co-Authored-By: Claude ...`), and pull request descriptions with its "Generated with" line. Keep
commit messages short and in plain words: what changed and why.
